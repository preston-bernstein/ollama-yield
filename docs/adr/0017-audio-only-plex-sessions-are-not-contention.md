# Audio-only Plex sessions are not Contention

**Status: accepted; implemented in `internal/plex/plex.go` (`session`, `audioSessionElement`, `mediaContainer.Sessions`, `ActiveSession`). Refines ADR-0012; does not change `internal/detect` or `internal/yield`.**

ADR-0012 added a `/status/sessions` check so background maintenance would stop causing a Yield, because matching the `"Plex Transcoder"` process name alone could not tell real playback from Plex's own scheduled work. That fixed the case where nobody was watching. It did not fix the case where someone is **listening**: `ActiveSession()` read only the container's `size` attribute, so any session at all — including a music stream — corroborated the process match and produced Contention.

The cost was measured on 2026-09-22. Over a 48h window every one of 86 Yield entries carried `reason="plex"` while the GPU sat at 3% utilisation, and the live session was a `<Track>`. Yield's action is `cancel in-flight + unload VRAM` (ADR-0003), so each entry ended LightRAG's in-flight embedding calls: 151 embed requests were preempted, and 100% of the minutes containing a preemption also contained a Yield — none fell outside one. Downstream, `NanoVectorDBStorage[chunks]` could not flush, the ingest pipeline halted, and algo-corpus sat at 69 documents parsing / 20 analyzing / 1 processed with `docs_processed` frozen since 2026-07-27. Loudness analysis — one of the very background tasks ADR-0012 names — is itself audio work that runs the transcoder binary, so listening to music reliably lit both signals at once.

**Decision: a session that is provably audio-only does not report Contention.** `mediaContainer` now collects child elements (`xml:",any"`) and reads each one's element name. `ActiveSession()` returns false only when the container declares at least one session, lists exactly as many as it declared, and every one of them is a `<Track>`. This restores the definition CONTEXT.md already gave — Contention is "gaming, or Plex video **transcoding**" — which the code had drifted from; it is a correction to match the documented contract, not a new policy.

**The yield-to-gaming invariant is not weakened, and the exclusion fails toward Yielding.** ADR-0004's law ("the only law is yielding to gaming") is about *what the Broker owes a real GPU claim*, and an audio stream was never one. Nothing about detection latency, the Yield action, or the heavy path changes: a video session still enters Yield on the same poll it always did. Every uncertain case resolves toward Contention — a `<Video>` or `<Photo>` session, a mixed container with music playing alongside a video stream, an element name this code has never seen, a container whose declared `size` does not match what it listed, and (unchanged from ADR-0012) any transport or decode error. The asymmetry is the one `broker-graded-yield-frontier` states: a missed Yield can stutter someone's game, a spurious Yield only delays batch work, so classifier errors must land on the Yield side. This is the "refining detection" direction that document sanctions, not the graded-yield frontier itself — no request runs *concurrently* with a real GPU claim here.

**Rejected: keying on `<TranscodeSession videoDecision="transcode">` instead of the element name.** This is the more precise signal — it would also skip Yield for direct-play video, which genuinely does not transcode — but it requires knowing the exact shape Plex emits for a transcoding video session, and no such capture was available when this was written. The audio fixture in `plex_audio_test.go` is a real capture from the desktop server; a video fixture would have been written from assumption. A detector whose fail-safe branch is guessed is worse than a narrower one whose suppression branch is verified, because the guess only shows up as a missed Yield during a real transcode — a game stutter, the one outcome ADR-0003 forbids. Direct-play video therefore still yields, conservatively, and this stays open as a follow-up once a real transcoding-session capture exists.

**Rejected: raising `BROKER_BATCH_WAIT` so batch work outlasts a Yield.** Investigated first and abandoned. `docs/embed-lane-parking/` NFR-2 fixes `BROKER_PARK_HOLD + BROKER_BATCH_WAIT` at 900s of LightRAG's 1200s budget and states the remaining ~300s is serve-plus-retry budget, "not slack"; raising the wait would consume it and break an invariant that `internal/config/config_test.go` exists to hold. It also treats the symptom — the requests were being ended by a Yield that should never have started, and no wait budget survives `cancel in-flight`.

**Rejected: a config flag to opt out of audio suppression.** A new env var would have to touch all five surfaces this repo's change control requires, to express a choice with no defensible "on" setting: nobody wants the GPU yielded for music. Behavior this narrow belongs in the detector, not in an operator's hands.

**Links**: ADR-0012 (Plex session corroboration — this refines its check), ADR-0003 (hard yield + VRAM unload — the action whose cost makes a false positive expensive), ADR-0004 (GPU scheduling policy — the invariant preserved here), ADR-0009 (embed-lane parking — protects *queued* batch requests during a Yield, but cannot protect in-flight ones, which is why the false Yield had to be stopped at the source).
